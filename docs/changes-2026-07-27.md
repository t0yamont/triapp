explaining why, following the convention already used elsewhere in the engine. Writing a test
that fakes unreachable input would have produced a green number that proves nothing.

## 2. Swim sessions are written as sets (§7.2)

The last remaining "not built" item from `docs/algorithm-review-2026-07.md` §2.5.

**The bug.** `renderSession` sent every non-VO₂ swim through its generic branch, which emits one
continuous effort. So a 40-minute technique swim rendered as a **single steady 40-minute block** —
a prescription no coach would write, because a pool set is broken by the wall. This was reaching
the athlete, not just sitting wrong in a data structure.

**The fix.** Swim sessions now render as sets:

- **technique** — alternates a drill with a swim, then short rest
- **everything else** (aerobic volume, recovery) — straight sets with short rest
- **VO₂** — untouched; §7.2 already specifies 10 × 100 at CSS and that path still owns it

Session totals and target zones are unchanged. Only the shape changed, and the total still
reconciles exactly to the requested duration for every input tested (20/33/40/47/60 min).

**`drill` became its own `StepIntent`.** It was tempting to reuse `work`, but scoring a drill as
work would inflate the session's load, and calling it `recovery` would hide that the athlete is
doing something deliberate. Nothing outside the module consumed `StepIntent`, so widening the
union was safe.

**Constants note.** The set and drill lengths are *structural* — how a session is written on a
whiteboard — not physiological claims, and they are commented as such. They are not in
`constants.ts` because they are not physiology; the one genuinely physiological swim template
(§7.2's 10 × 100) already lives there and was not touched.

the 200 m / 400 m trial and calls `fitCriticalSwimSpeed`, with its own error vocabulary for
swapped or sprint-paced trials. I verified this rather than rebuilding it. Worth correcting in
the vault.

**Five open items still need your decision.** These are not work I can do — they are judgement
calls about the product, and guessing at any of them would put an invented number somewhere it
would look authoritative:

1. **Heat trigger margin** (°C wet-bulb) — §7.4 says "a defined margin" and never defines it.
   Still a required caller input rather than a constant.
2. **Swim IF direction** — §5.1 defines swim `IF = CSS speed / actual speed`, which inverts
   (IF > 1 when swimming *easier* than CSS).
3. **Minimum plan weeks / entry requirements sign-off** — implemented with values cross-checked
   against several coaching sources, but still convention rather than physiology.
4. **G2 semantics** — confirm the peak-based reading (`D-G2-PEAK`).
5. **Readiness-to-start gate** — should an under-prepared athlete be blocked or warned?

**Remaining roadmap work is integration, not engine.** Phase 7 (Garmin push, Expo mobile,
HealthKit, notifications) and Phase 8 (data export/delete, consent versioning, observability)
are the substantive remainder. The physiology engine itself now implements every section of
`03-ALGORITHM.md` that does not depend on one of the five decisions above.
