## 2. Swim sessions are written as sets (§7.2)

The last remaining "not built" item from `docs/algorithm-review-2026-07.md` §2.5.

**The bug.** `renderSession` sent every non-VO₂ swim through its generic branch, which emits one
continuous effort. So a 40-minute technique swim rendered as a **single steady 40-minute block** —
a prescription no coach would write, because a pool set is broken by the wall. This was reaching
the athlete, not just sitting wrong in a data structure.

**The fix.** Swim sessions now render as sets:

- **technique** — alternates a drill with a swim, then short rest
- **everything else** (aerobic volume, recovery) — straight sets with short rest
- **VO₂** — untouched; §7.2 already specifies 10 × 100 at CSS and that path still owns it

Session totals and target zones are unchanged. Only the shape changed, and the total still
reconciles exactly to the requested duration for every input tested (20/33/40/47/60 min).

**`drill` became its own `StepIntent`.** It was tempting to reuse `work`, but scoring a drill as
work would inflate the session's load, and calling it `recovery` would hide that the athlete is
doing something deliberate. Nothing outside the module consumed `StepIntent`, so widening the
union was safe.

**Constants note.** The set and drill lengths are *structural* — how a session is written on a
whiteboard — not physiological claims, and they are commented as such. They are not in
`constants.ts` because they are not physiology; the one genuinely physiological swim template
(§7.2's 10 × 100) already lives there and was not touched.

## 3. The five open questions — resolved

Delegated by the owner. Full reasoning in `DECISIONS.md`; each is written so it can be reversed
on evidence rather than re-argued.

### Two needed code

**`D-SWIM-IF` — the spec formula is inverted; implemented correctly.** §5.1 writes swim
`IF = CSS speed / actual speed`, which makes IF *rise* as the athlete swims easier. A recovery
swim would have out-scored a threshold set, and the resulting sTSS would corrupt CTL/ATL for
anyone who swims. Now `actual / CSS`, matching every other sport. F6 pins only the cubic
exponent, so no golden fixture moved. The test now proves the *direction* (easy < 1 < hard)
instead of pinning the old behaviour.

**`D-HEAT-MARGIN` — 3 °C wet-bulb, as product policy.** Leaving it a required input meant the UI
had to ask a question no athlete can answer, so `HEAT_TRIGGER_MARGIN_C = 3` is now a default
(still overridable). Set low because the risks are asymmetric: the preferred intervention is
20–30 min of passive sauna that costs no training quality, while an unacclimated athlete in a hot
race risks heat illness. It is labelled product policy, **not** a cited physiological threshold.

### Three were sign-offs

- **Minimum weeks / entry requirements** — stand as convention. They gate advice and warnings,
  never safety limits, so a wrong value produces worse guidance rather than an unsafe plan.
- **`D-G2-PEAK`** — confirmed. The per-week reading contradicts G4's mandated recovery cut.
- **Readiness-to-start gate** — stays a **warning**, never a block. The baseline is self-reported,
  so blocking just teaches athletes to enter a better number, leaving the engine planning from a
  fiction *and* having lost their trust. A warning keeps the honest answer worth giving, which is
  what the rest of the adaptive system depends on.

## 4. Phase 7 — execution & device sync

Garmin's Training API needs partner credentials that don't exist yet, so I built the two parts
that can be proven without them — deliberately the two the roadmap itself prioritises.

### FIT workout export (`packages/core/ingest/encode/fitWorkout.ts`)

The roadmap's risk table names this as the fallback to build **"regardless"** of whether the
Training API grant arrives; it also serves any device the API never reaches. Writes a planned
session as a Garmin-compatible `.FIT` file — `file_id`, `workout`, `workout_step`, little-endian,
one definition per global message. HR targets encode as bpm + 100 per the format; a step with no
range is written *open* rather than given an invented target. Reuses the existing `fitCrc`.

The test walks the file back out with an **independent minimal reader** rather than asserting on
bytes the encoder just produced — that proves the output is parseable, not merely deterministic.
It covers both CRCs, the declared data size, name truncation, non-ASCII stripping, and the sport
enums.

### Device push policy (`packages/api-client/src/devices/push.ts`)

The **10-day rolling window** and **republish-on-mutation** rules, as pure functions with no HTTP,
so the decision stays testable without credentials and the transport becomes a thin shell.

- Pushes what's imminent, not the whole season — an adaptive plan shouldn't leave months of stale
  sessions on a watch.
- Republishes anything the engine changed after it was sent. Training a session the engine has
  since eased is exactly what an adaptive plan exists to prevent.
- Withdraws future sessions that fall out of the window or leave the plan entirely, but **leaves a
  past session alone** — the athlete may still be about to complete it.

### Still needs credentials or native tooling

The Garmin HTTP client, the Expo app, HealthKit, push notifications, and the EAS/TestFlight
pipeline. None can be meaningfully built or verified from here; the push policy above is the
piece the HTTP client will wrap.
